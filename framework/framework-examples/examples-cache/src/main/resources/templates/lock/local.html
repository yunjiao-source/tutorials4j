🔒 无限阻塞模式 waitTime = -1 (lock.lock)

@LocalLockable(prefix = "order:", key = "#root.args[0]", waitTime = -1)

⚠️ 真实行为警告：waitTime ≤ 0 时，切面调用 localLockService.doInLock(key, () -> joinPoint.proceed())
底层使用 lock.lock() → 线程会无限阻塞直到获得锁，不会超时，不会快速失败。
如果第一个请求耗时较长（如睡眠9秒），后续请求将一直排队等待，可能导致请求堆积。

当前后端固定订单号 "1"，所有请求竞争同一把锁 order:1。

⏳ 超时等待模式 waitTime = 3000 ms (tryLock)

@LocalLockable(prefix = "order:", key = "#root.args[0]", waitTime = 3000)

✅ 真实行为：切面调用 localLockService.doInLock(key, Duration.of(3000, MILLIS), () -> joinPoint.proceed())
底层使用 lock.tryLock(3000, MILLISECONDS) → 最多等待3秒，超时抛出 LockCreateException。

支持动态订单号，不同订单号锁隔离，相同订单号竞争锁并等待超时。

测试指南（根据真实锁行为）
  • 无限阻塞模式（左）：快速连续点击按钮，第一个请求会获得锁并随机睡眠 0~9 秒，后续请求会无限阻塞排队，直到前一个释放锁。您会看到请求耗时逐次累加（比如第一个耗时3秒，第二个耗时3+5秒...），不会超时失败。刷新页面可以中断请求（演示风险）。
  • 超时等待模式（右）：对相同订单号连续点击，第一个请求睡眠 0~9 秒，后续请求最多等待3秒。若3秒内锁未释放则请求失败（HTTP 500，日志显示锁创建异常）。不同订单号之间锁不互斥，可并行执行。
  • 业务方法内部 ThreadLocalRandom.current().nextInt(10) 随机睡眠秒数，模拟耗时操作。
  • 日志显示每个请求的端到端耗时（包含锁等待+业务睡眠+网络）。
