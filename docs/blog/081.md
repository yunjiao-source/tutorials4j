# 081-缓存模块-基于 Redis + AOP 的幂等性守卫设计与实现

本文章代码: [gitee](https://gitee.com/yunjiao-source/tutorials4j) , [gitcode](https://gitcode.com/yun-jiao/tutorials4j) , [github](https://github.com/yunjiao-source/tutorials4j)

在分布式系统与微服务架构中，接口幂等性是一项基础且至关重要的设计原则。幂等性保证了同一操作无论执行多少次，其结果与执行一次完全相同，从而避免因网络重试、客户端重复提交等造成的数据重复或业务异常。本文以一套基于 Spring Boot、Redis 和 AOP 的幂等性守卫组件为例，深入剖析其设计思想、核心实现及自动配置机制，并附带完整的示例代码。

---

## 一、幂等性需求与设计方案

### 1.1 痛点场景
- **表单重复提交**：用户因网络延迟多次点击提交按钮。
- **RPC 重试**：服务调用方因超时未收到响应而重试，但实际服务已处理成功。
- **消息重复消费**：消息队列重复投递消息。

### 1.2 常见实现方式
| 方式 | 说明 |
|------|------|
| 数据库唯一索引 | 利用业务字段唯一约束，插入重复数据报错 |
| 分布式锁 | 对业务唯一标识加锁，保证同一时间只有一个请求处理 |
| Token 机制 | 前端请求前获取 token，服务端校验并销毁 |
| Redis 原子操作 | 利用 `SETNX` 或 `setIfAbsent` 作为“轻量锁” |

本文选用 **Redis 原子操作 + 方法拦截**（AOP）的方式，具有低侵入、高性能、分布式一致的特点。

### 1.3 整体组件
本实现包含以下模块：
- **`@IdempotentGuard`**：声明式注解，标记需要幂等保护的方法。
- **`IdempotentGuardAspect`**：AOP 切面，拦截注解方法，执行 Redis 键检查与写入。
- **`RedisTemplateDecorator`**：封装 Redis 模板，支持租户前缀的序列化。
- **`RedisCacheConfiguration`**：Spring Boot 自动配置，装配切面及其他核心 Bean。
- **示例模块**：`OrderController` 与 `OrderService` 演示用法。

## 二、核心代码详解

### 2.1 幂等守卫注解：`@IdempotentGuard`

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
@Documented
public @interface IdempotentGuard {
    String prefix() default "";
    String key();
    long expireTime() default 1;
    TimeUnit timeUnit() default TimeUnit.HOURS;
}
```

**属性说明：**
- `prefix`：Redis 键的前缀，便于按业务区分，支持留空。
- `key`：**必填**，SpEL 表达式，用于动态生成业务唯一标识（如订单号、用户ID组合）。
- `expireTime` + `timeUnit`：幂等记录的过期时间，默认 1 小时。过期后自动清理，允许相同请求再次处理（但通常业务要求永久幂等，可根据场景调整）。

### 2.2 AOP 切面：`IdempotentGuardAspect`

切面是幂等守卫的核心执行者，代码如下（简化）：

```java
@Around("@annotation(idempotentGuard)")
public Object around(ProceedingJoinPoint joinPoint, IdempotentGuard idempotentGuard) throws Throwable {
    // 1. 解析 SpEL 获取动态 key 值
    String value = spelEvaluator.getValue(method, args, idempotentGuard.key(), String.class);
    String key = idempotentGuard.prefix() + value;

    // 2. 原子尝试设置键
    Boolean success = redisTemplate.opsForValue()
        .setIfAbsent(key, Instant.now().toString(), 
                     Duration.of(expireTime, timeUnit.toChronoUnit()));

    if (Boolean.TRUE.equals(success)) {
        return joinPoint.proceed();  // 首次执行
    } else {
        throw CacheErrorCode.IDEMPOTENT_FAIL.throwed().param("key", key);
    }
}
```

**关键设计点：**
- **SpEL 动态键**：支持方法参数、上下文变量，灵活适配各种业务标识。
- **原子操作 `setIfAbsent`**：底层对应 Redis `SET key value NX EX` 命令，保证分布式环境下“有且仅有一次”的写入成功。
- **失败即抛异常**：若键已存在，视为重复请求，抛出幂等失败异常，由全局异常处理器返回友好提示。
- **时间戳作为值**：存储当前时间仅用于可观测性，实际只需关心键的存在性。

**注意事项：**
- 切面方法必须使用 `@Around` 并手动调用 `proceed()`，确保业务逻辑仅在首次执行。
- 若业务方法内部抛出异常，Redis 键不会被自动删除，可结合业务补偿机制（但一般异常不会导致重复执行，因此幂等记录仍可保留以防重试）。

### 2.3 自动装配：`RedisCacheConfiguration`

该配置类在 Spring Boot 启动时自动注册所有必要 Bean，包括：

- `RedisTemplateDecorator`：采用 `TenantKeySerializer` 为所有键自动添加租户前缀，实现多租户隔离。
- `RedisLockService` 与 `RedisLockableAspect`：分布式锁组件（非本文重点，但一并装配）。
- **`IdempotentGuardAspect`**：通过 `@Bean` 方式装配，依赖 `SpelMethodBasedExpressionEvaluator` 和 `RedisTemplateDecorator`。

```java
@Bean
@ConditionalOnMissingBean
IdempotentGuardAspect idempotentGuardAspect(
    SpelMethodBasedExpressionEvaluator spelMethodBasedExpressionEvaluator,
    RedisTemplateDecorator redisTemplateDecorator) {
    return new IdempotentGuardAspect(spelMethodBasedExpressionEvaluator, redisTemplateDecorator);
}
```

**为何用 `@ConditionalOnMissingBean`？**  
允许开发者覆盖默认切面实现，或自定义 `SpelMethodBasedExpressionEvaluator`，提高扩展性。

## 三、使用示例解析

### 3.1 控制器与业务服务

`OrderController` 提供 REST 接口，调用 `OrderService.handler`：

```java
@RestController
@RequestMapping("order")
public class OrderController {
    private final OrderService orderService;

    @PostMapping("/{orderId}")
    public String handler(@PathVariable("orderId") String orderId) {
        return orderService.handler(orderId);
    }
}
```

`OrderService` 使用注解声明幂等保护：

```java
@Component
public class OrderService {
    @IdempotentGuard(
        prefix = "idempotent:order:",
        key = "#orderId",
        expireTime = 30,
        timeUnit = TimeUnit.SECONDS)
    public String handler(String orderId) {
        // 业务处理（例如更新订单状态、扣减库存等）
        return "订单处理成功";
    }
}
```

### 3.2 请求流程

1. 客户端 POST `/order/12345`。
2. 切面解析 `#orderId` 为 `"12345"`，生成 Redis 键 `idempotent:order:12345`。
3. 尝试 `setIfAbsent`，若成功（键不存在），执行业务方法并返回成功。
4. 若同一订单号在 30 秒内再次请求，`setIfAbsent` 返回 `false`，抛异常 → 响应幂等失败。

**效果**：30 秒内无论重试多少次，业务逻辑只执行一次，避免重复处理。

## 四、高级特性与扩展思考

### 4.1 租户前缀支持

`TenantKeySerializer` 会为所有键添加租户标识（例如 `tenantId:`），本例中的 `prefix` 可以与之共存，形成 `租户:业务前缀:业务标识` 的完整键结构，完美适配 SaaS 多租户场景。

### 4.2 过期时间的业务含义

- **短过期**（如 30 秒）：适用于高频操作，防止短时间内重复提交，过期后允许再次处理（但非绝对幂等）。
- **长过期**（如 1 天）：适用于订单创建等不可逆操作，确保业务“永久”幂等。
- **无限期**：若业务要求永久幂等，可将过期时间设为极大值（如 `TimeUnit.DAYS.toSeconds(3650)`）。

### 4.3 异常处理与反馈

切面抛出的 `CacheErrorCode.IDEMPOTENT_FAIL` 可被全局异常拦截，返回明确的错误信息（如 `{"code": "IDEMPOTENT_FAIL", "message": "重复请求"}`），便于前端识别并提示用户。

### 4.4 与分布式锁的区别

| 特性 | 幂等守卫 | 分布式锁 |
|------|----------|----------|
| 目的 | 防止重复执行 | 防止并发冲突 |
| 锁粒度 | 业务唯一键 | 共享资源键 |
| 阻塞行为 | 直接拒绝 | 阻塞等待或快速失败 |
| 典型场景 | 订单提交、支付回调 | 库存扣减、配置更新 |

幂等守卫属于“轻量锁”，不阻塞等待，直接失败，适合高频幂等校验；分布式锁则适用于需要互斥执行的临界区。

### 4.5 潜在问题与改进

- **异常情况下的键清理**：如果业务方法执行失败（如数据库异常），建议在业务层捕获并手动删除 Redis 键，以便重试。切面未处理此点，可扩展为支持 `@IdempotentGuard(clearOnFailure = true)`。
- **Redis 高可用**：需确保 Redis 集群可靠，否则幂等守卫失效。
- **键值内容**：当前仅存储时间戳，可增加机器信息或请求追踪 ID，便于链路追踪。

## 五、总结

本文详细剖析了一套基于 Redis + Spring AOP 的幂等性守卫组件，从注解定义、切面逻辑、自动配置到实际应用示例，展现了其**低侵入、高扩展、分布式一致**的优良特性。该设计已在生产环境中稳定运行，有效解决了接口重复调用带来的数据重复问题。

开发者只需在服务方法上添加一行注解，即可轻松获得幂等保护，极大提升了开发效率与系统健壮性。未来可根据业务需求扩展诸如错误重试策略、键失效监听等高级功能，使其更加完善。
