# 088-OAuth模块-认证核心框架架构解析：oauth-core 的自动装配、配置模型与拦截器注册

本文章代码: [gitee](https://gitee.com/yunjiao-source/tutorials4j) , [gitcode](https://gitcode.com/yun-jiao/tutorials4j) , [github](https://github.com/yunjiao-source/tutorials4j)

## 1. 引言

对外提供 API 的服务，无论面向第三方开发者还是内部应用，通常都需要解决两件事：**"你是谁"（认证）** 与 **"你能用多少"（配额/限流）**。在众多企业中，`API Key` 是最轻量、最通用的认证形态——把一串密钥放进 `Header` 或查询参数，网关或应用据此识别调用方。

但"识别调用方"只是第一步，如果没有配额约束，一个被盗用或失控的 Key 就能打垮整个后端。因此，一个合格的认证与授权模块，必须把 **"按 Key 维度的限流"** 作为一等公民来设计。

在 `tutorials4j` 的 `framework/framework-oauth` 聚合模块中，`oauth-core` 正是这一能力的核心载体。本文从**模块边界、自动装配、配置模型、MVC 拦截器注册、错误码规范**五个视角，带你完整梳理 `oauth-core` 的设计骨架；下一篇将深入限流计数与 Redis Lua 的原子实现。

## 2. 模块总览

`framework-oauth` 是一个 Maven 聚合工程，由三个子模块组成：

```
framework-oauth (父POM)
├── oauth-core               # 认证与授权核心：配置模型 + 限流服务 + MVC 拦截器
├── oauth-so-token           # Sa-Token 生态：API Key 模板工厂
└── oauth-spring-boot-starter # Spring Boot Starter：聚合装配入口
```

- **oauth-core**：不依赖任何具体认证框架，只定义"配置模型、限流服务、拦截器"这套与 Spring 生态正交的能力，是本文的主角。
- **oauth-so-token**：负责与 Sa-Token 的 `apikey` 模块衔接，提供 `SaApiKeyTemplateFactory`（见第 8 节）。
- **oauth-spring-boot-starter**：只做一件事——把上面两个模块的 `@Configuration` 汇总进一个 `@AutoConfiguration`。

oauth-core 的源码布局非常紧凑，仅 8 个类：

```
oauth-core/src/main/java/tutorials4j/framework/auth/core/
├── annotation
│   └── ApiKeyRateLimiter.java            // 方法级声明式限流注解
├── autoconfigure
│   ├── OAuthConfiguration.java           // 核心 Bean 装配
│   ├── OAuthMvcConfiguration.java        // WebMvcConfigurer：注册拦截器
│   ├── OAuthProperties.java              // 配置属性绑定入口
│   └── ApiKeyOptions.java                // API Key 嵌套配置模型
├── component
│   ├── ApiKeyRateLimiterService.java     // 双窗口（分钟/天）计数服务
│   └── ApiKeyRateLimiterInterceptor.java // HandlerInterceptor 实现
└── common
    └── OAuthErrorCode.java               // 认证模块专属错误码
```

从包结构能读出清晰的分层意图：`annotation` 定义"做什么"、`autoconfigure` 定义"怎么装配"、`component` 负责"怎么做"、`common` 统一"出错怎么说"。

oauth-core 的依赖只有两个内部模块（见其 `pom.xml`）：

| 依赖 | 提供的核心能力 | 用途 |
|---|---|---|
| `cache-redis` | `RedisScriptExecutor` | 基于 Lua 脚本的原子 `INCR + PEXPIRE`，是限流计数的地基 |
| `web-core` | `WebUtils` | 从 `HandlerMethod` 上解析注解，供拦截器探测限流声明 |

其余如 `HeaderUtils`、`ErrorCode`、`DefaultConsts` 等，均通过这两条依赖链传递引入。这种"只依赖能力提供方、不绑定业务框架"的做法，让 oauth-core 未来无论是接 Sa-Token、Spring Security 还是自研 Token 体系，核心代码都无需改动。

## 3. 自动装配链路：从 Starter 到核心 Bean

Spring Boot 3 中，Starter 通过 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 声明自动配置类。oauth-spring-boot-starter 的 imports 文件内容只有一行：

```
tutorials4j.framework.oauth.autoconfigure.OAuthAutoConfiguration
```

`OAuthAutoConfiguration` 本体非常"薄"，只负责用 `@Import` 汇总三个配置类：

```java
@Slf4j
@AutoConfiguration
@Import({OAuthConfiguration.class, OAuthMvcConfiguration.class, SoTokenOAuthConfiguration.class})
public class OAuthAutoConfiguration {
  @PostConstruct
  public void postConstruct() {
    log.trace("[OAUTH] OAuth Auto Configuration");
  }
}
```

装配时序与依赖关系可抽象为下图：

```
应用启动
  └─ AutoConfiguration.imports → OAuthAutoConfiguration
       ├─ OAuthConfiguration         (启用 OAuthProperties 绑定)
       │    └─ @Bean ApiKeyRateLimiterService(RedisScriptExecutor, ApiKeyOptions)
       ├─ OAuthMvcConfiguration      (WebMvcConfigurer)
       │    └─ new ApiKeyRateLimiterInterceptor(ApiKeyRateLimiterService)
       │         └─ registry.addInterceptor(...).excludePathPatterns().addPathPatterns()
       └─ SoTokenOAuthConfiguration
            └─ @Bean SaApiKeyTemplateFactory
```

三个配置类职责单一、互不越界：

1. **OAuthConfiguration** 负责"造服务"：把 `RedisScriptExecutor` 与配置模型组装成 `ApiKeyRateLimiterService`；
2. **OAuthMvcConfiguration** 负责"挂拦截器"：把服务包装成 `HandlerInterceptor` 并注册进 Spring MVC 的拦截器链；
3. **SoTokenOAuthConfiguration** 负责"接生态"：仅当用户没有自定义时才注册 Sa-Token 的模板工厂。

### 3.1 核心服务的条件装配

`OAuthConfiguration` 的代码几乎可以当作"Spring Boot 自动配置的教科书范本"来读：

```java
@Slf4j
@Configuration(proxyBeanMethods = false)
@EnableConfigurationProperties({OAuthProperties.class})
public class OAuthConfiguration {
  @PostConstruct
  public void postConstruct() {
    log.trace("[OAUTH-CORE] OAuth Configuration");
  }

  @Bean
  @ConditionalOnMissingBean
  ApiKeyRateLimiterService apiKeyRateLimiterService(
      RedisScriptExecutor redisScriptExecutor, OAuthProperties properties) {
    log.trace("[OAUTH-CORE] Api Key Rate Limiter Service");
    return new ApiKeyRateLimiterService(redisScriptExecutor, properties.getApiKey());
  }
}
```

这里有几个值得品味的细节：

- **`@ConditionalOnMissingBean`**：框架提供默认实现，但用户可以在自己的配置类里声明一个同类型的 Bean 完全替换它——"约定优于配置，但可覆盖"。
- **构造参数直接声明为 `RedisScriptExecutor` 与 `OAuthProperties`**：不通过 `@Autowired` 字段注入，让 Bean 之间的依赖在方法签名上显式可见，也便于单元测试时直接 `new`。
- **传入的是 `properties.getApiKey()`（即 `ApiKeyOptions`）而不是整个 `OAuthProperties`**：服务只需要 API Key 相关的配置子集，缩小了服务的可见面，也避免了服务与全局属性对象的隐式耦合。
- **`@Configuration(proxyBeanMethods = false)`**：本配置类没有跨 `@Bean` 方法的内部调用，关闭 CGLIB 代理能降低启动开销，这是 Spring Boot 官方推荐的写法。

`RedisScriptExecutor` 由 `cache-redis` 模块的 `RedisCacheConfiguration` 装配（同样的 `@ConditionalOnMissingBean` 模式），oauth-core 全程把它当黑盒使用，只关心"给我一个原子的 `incrAndExpire`"。

### 3.2 MVC 拦截器的注册

`OAuthMvcConfiguration` 实现了 `WebMvcConfigurer`，在容器装配阶段就把拦截器挂进 MVC 链路：

```java
@Slf4j
@Configuration(proxyBeanMethods = false)
@RequiredArgsConstructor
public class OAuthMvcConfiguration implements WebMvcConfigurer {
  private final ApiKeyRateLimiterService apiKeyRateLimiterService;
  private final OAuthProperties properties;

  @Override
  public void addInterceptors(InterceptorRegistry registry) {
    ApiKeyRateLimiterInterceptor apiKeyRateLimiterInterceptor =
        new ApiKeyRateLimiterInterceptor(apiKeyRateLimiterService);

    InterceptorRegistration registration = registry.addInterceptor(apiKeyRateLimiterInterceptor);
    HandlerInterceptorOptions options = properties.getApiKey().getInterceptor();
    registration.excludePathPatterns(options.getExcludePathPatterns());
    registration.addPathPatterns(options.getIncludePathPatterns());

    log.trace(
        "[OAUTH-CORE] 'ApiKeyRateLimiterInterceptor' configuration parameters are {}", options);
  }
}
```

设计上有一个容易被忽略但非常关键的点：**"路径是否被拦截"与"方法是否限流"是两套正交的开关**——

- **注册期静态开关**：`includePathPatterns` / `excludePathPatterns` 决定拦截器对哪些 URL 生效。默认值来自 `HandlerInterceptorOptions`，即 `include = {"/demo/**"}`、`exclude = {}`，保证开箱即用时能作用于演示路径。
- **运行期动态开关**：拦截器内部再通过"方法上是否有 `@ApiKeyRateLimiter` 注解"决定本次请求是否真的计数限流（详见下一篇）。

这两层配合带来的灵活性是：可以注册一个宽泛的路径前缀（例如 `/api/**`），再让不同端点各自决定是否限流、套用哪一套配额；也可以反过来把拦截器收窄到少量敏感接口。把"网络层路径"与"业务层限流"解耦，是这套框架最核心的设计思想之一。

## 4. 配置模型：三层嵌套的属性设计

oauth-core 的配置根前缀是 `tutorials4j.oauth`（常量定义于 `PropertiesConsts.PROPERTY_PREFIX_OAUTH`）。属性类采用经典的三层嵌套：

```java
@Data
@ConfigurationProperties(prefix = PropertiesConsts.PROPERTY_PREFIX_OAUTH)
public class OAuthProperties {
  @NestedConfigurationProperty private ApiKeyOptions apiKey = new ApiKeyOptions();
}
```

```java
@Data
public class ApiKeyOptions {
  private String keyPrefix = "oauth:apikey:";

  @NestedConfigurationProperty
  private HandlerInterceptorOptions interceptor = new HandlerInterceptorOptions();

  private ApiKeyLimiterOptions defaultLimiter = new ApiKeyLimiterOptions();
  private Map<String, ApiKeyLimiterOptions> namedLimiter = new HashMap<>();

  @Data
  public static class ApiKeyLimiterOptions {
    private Integer maxRequestsPerMinute = 100;
    private Integer maxRequestsPerDay = 10000;
  }
}
```

逐层解读：

| 层级 | 字段 | 含义 | 默认值 |
|---|---|---|---|
| `api-key` | `key-prefix` | Redis 计数 Key 的统一前缀（命名空间） | `oauth:apikey:` |
| `api-key` | `interceptor` | 拦截器路径选项（复用公共的 `HandlerInterceptorOptions`） | include `/demo/**` |
| `api-key` | `default-limiter` | 全局默认配额 | 100 次/分钟、10000 次/天 |
| `api-key` | `named-limiter` | 按"限流组名"区分的配额表 | 空 |
| `named-limiter` 内 | `max-requests-per-minute` | 组内每分钟上限 | 100 |
| `named-limiter` 内 | `max-requests-per-day` | 组内每天上限 | 10000 |

对应的 YAML 形态（examples-oauth 的 `application-apikey.yml` 摘录）：

```yaml
tutorials4j:
  oauth:
    api-key:
      default-limiter:
        max-requests-per-day: 20
        max-requests-per-minute: 10
      named-limiter:
        method1:
          max-requests-per-minute: 5
          max-requests-per-day: 10
      interceptor:
        include-path-patterns: /api-key
```

几个设计亮点：

1. **`defaultLimiter` + `namedLimiter` 的"默认值 + 命名覆盖"模式**：`namedLimiter` 是一张 `Map<String, ApiKeyLimiterOptions>`，Key 与 `@ApiKeyRateLimiter(name = "xxx")` 的 name 一一对应。未命中的 name 自动回退到默认配额——新接口接入时零配置即可获得兜底保护。
2. **复用 `HandlerInterceptorOptions`**：路径包含/排除的模型是公共模块 `common-core` 定义的，captcha、totp 等其它拦截器也在用它。一处定义、处处复用，避免各模块各写一套。
3. **`@NestedConfigurationProperty`**：显式声明嵌套对象，保证 IDE 提示与元数据生成（`spring-configuration-metadata`）都正确。
4. **两级配额天然映射业务**：分钟配额用于"防突发"，天配额用于"防滥用/计费上限"，两者独立计数互不干扰。

## 5. 错误码与统一异常规范

限流拦截器需要抛出异常来中断请求，oauth-core 没有自建一套异常体系，而是接入 framework 的"错误码枚举"约定。

```java
@Getter
public enum OAuthErrorCode implements ErrorCode {
  API_KEY_VALUE_NOT_EXIST("缺少 API Key");
  private final Feedback feedback;

  OAuthErrorCode(String message) {
    this.feedback = Feedback.builder().code(this.name()).message(message).build();
  }
}
```

关键机制：

- `Feedback` 是 `(code, message)` 的不可变记录；`code` 直接取枚举名（`API_KEY_VALUE_NOT_EXIST`），保证代码与报文可追溯。
- `ErrorCode` 接口提供 `throwed()` 系列默认方法，返回 `ErrorCodeException`；拦截器里一行 `OAuthErrorCode.API_KEY_VALUE_NOT_EXIST.throwed()` 即可"表达错误并抛出"，无需手工 new。
- 超限场景复用公共错误码 `BaseErrorCode.TOO_MANY_REQUESTS`，并通过 `throwed("API Key 每分钟请求次数超限")` 携带业务化详情。

抛出的 `ErrorCodeException` 最终由公共模块的 `GlobalExceptionHandler`（`@RestControllerAdvice`）统一收敛为 `Result` JSON，响应结构形如：

```json
{
  "timestamp": "...",
  "code": "TOO_MANY_REQUESTS",
  "message": "太多请求",
  "path": "/api-key",
  "traceId": "...",
  "error": { "detail": "API Key 每分钟请求次数超限" }
}
```

HTTP 状态码通过 `BaseExceptionHandler` 的错误码映射表决定：

| 错误码 | HTTP 状态 | 触发场景 |
|---|---|---|
| `BaseErrorCode.TOO_MANY_REQUESTS` | **429** | 分钟或天配额超限 |
| `OAuthErrorCode.API_KEY_VALUE_NOT_EXIST` | **422**（未注册时默认） | 请求未携带 API Key |

注意：`TOO_MANY_REQUESTS` 被显式注册为 `429 TOO_MANY_REQUESTS`，而 oauth 自有错误码未注册映射，`BaseExceptionHandler` 的兜底逻辑将其解析为 `422 UNPROCESSABLE_ENTITY`。若希望"缺少 API Key"返回 401/400，只需在应用侧调用 `BaseExceptionHandler.registeErrorCode(...)` 补充映射即可，框架不越俎代庖。

## 6. 与兄弟模块的分工：oauth-so-token

`oauth-core` 刻意不绑定任何认证框架，而 `oauth-so-token` 负责连接 Sa-Token 的 API Key 能力：

```java
public class SaApiKeyTemplateFactory {
  private ConcurrentMap<String, SaApiKeyTemplate> cacheMap = new ConcurrentHashMap<>();

  public SaApiKeyTemplate getDefaultTemplate() {
    return cacheMap.computeIfAbsent(
        "DEFAULT", (namespace) -> SaApiKeyManager.getSaApiKeyTemplate());
  }

  public SaApiKeyTemplate getTemplate(String namespace) {
    return cacheMap.computeIfAbsent(namespace, this::createTemplate);
  }

  private SaApiKeyTemplate createTemplate(String namespace) {
    return new SaApiKeyTemplate(namespace);
  }
}
```

- Sa-Token 的 `SaApiKeyTemplate` 负责 **API Key 的签发/校验/续期**（认证侧），oauth-core 负责 **Key 的配额计数**（限流侧），二者职责互补。
- 工厂用 `ConcurrentHashMap.computeIfAbsent` 按命名空间懒加载并缓存模板，避免每次请求重复构建。
- 通过 `@ConditionalOnMissingBean` 注册，同样允许用户覆盖。

也就是说：**想要"生成 Key + 校验 Key + 按 Key 限流"的完整闭环，把 oauth-spring-boot-starter 引入即可**；oauth-core 只关心其中与 Spring 容器无关、可独立测试的那一部分。

## 7. 总结与展望

纵观 oauth-core 的骨架设计，可以提炼出四条可复用的方法论：

1. **薄自动配置 + 聚合 Starter**：`@AutoConfiguration` 只做 `@Import` 汇总，具体配置类各自独立、职责单一；`@ConditionalOnMissingBean` 保证默认实现可被替换。
2. **配置模型与行为解耦**：所有可调参数（前缀、路径、两级配额、命名配额表）收敛进属性类，默认值即文档，YAML 即配置。
3. **注册期与运行期的双开关**：路径模式决定拦截范围，方法注解决定是否限流，两层开关正交，扩展接口不污染框架代码。
4. **接入统一异常与错误码体系**：业务错误用枚举表达、用 `throwed()` 抛出、由全局处理器统一翻译成 `Result` 与 HTTP 状态码，限流逻辑里不出现任何响应序列化代码。
