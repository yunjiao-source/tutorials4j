# 083-消息模块-Spring Cloud Stream 多中间件适配实战——从代码结构看消息驱动设计

本文章代码: [gitee](https://gitee.com/yunjiao-source/tutorials4j) , [gitcode](https://gitcode.com/yun-jiao/tutorials4j) , [github](https://github.com/yunjiao-source/tutorials4j)

## 1. 项目概览
该示例是一个典型的**消息驱动微服务**，通过 Spring Cloud Stream 抽象了消息中间件（Kafka、RabbitMQ、NATS）的差异，让业务代码（短信发送）与底层 Broker 解耦。项目结构清晰：

- **主启动类** `ExampleMessageApplication` 标注 `@SpringBootApplication`，是 Spring Boot 标准入口。
- **配置类** `KafkaConfig` / `NatsConfig` / `RabbitConfig` 通过 `@Profile` 激活，并扫描 `tutorials4j.framework.examples.sms` 包，确保不同环境下加载相同的业务 Bean。
- **业务层**：`SmsController` 提供 REST 接口，`SmsProducer` 使用 `StreamBridge` 发送消息，`SmsConsumer` 定义 `java.util.function.Consumer` Bean 消费消息。
- **消息模型**：`SmsMessage` 包含手机号和内容。
- **配置文件**：`application.yml` 指定激活的 Profile，每个中间件有独立的 `application-{profile}.yml` 定义 binder 和 binding。

## 2. 为什么选择 Spring Cloud Stream？
传统方式下，每种 MQ 都有独立的 API，切换成本高。Spring Cloud Stream 提供统一的编程模型：
- **Binder** 抽象层负责与具体 Broker 交互。
- **Binding** 定义输入/输出通道与目的地（topic/exchange/queue）的映射。
- **函数式编程**（`Consumer`/`Supplier`/`Function`）替代注解监听，更简洁、可测试。

## 3. Profile 驱动的多环境配置
应用通过 `spring.profiles.active` 决定使用哪种中间件。三个配置类除了 Profile 名称外，都包含 `@ComponentScan` 扫描相同包——这保证了无论激活哪个 Profile，业务 Bean 都会被加载，而 Binder 实现则由 Spring Cloud Stream 根据 classpath 和配置自动选择。例如激活 `kafka` 时，`KafkaConfig` 会生效，但真正起作用的仍然是 `application-kafka.yml` 中的 `spring.cloud.stream.default-binder=kafka` 以及 Kafka 相关配置。

## 4. 消息生产与消费链路
- **生产者**：`SmsController` 收到 `POST /sms/send` 请求，生成一个自增手机号（从 13000000000 开始），调用 `smsProducer.sendSms()`。
- **发送**：`StreamBridge.send("sms-out-0", sms)` 将消息发送到名为 `sms-out-0` 的输出通道。该通道在配置中绑定到 destination（如 `sms-topic`），并由对应 Binder 转发。
- **消费者**：`SmsConsumer` 中定义了 `@Bean Consumer<SmsMessage> sms()`，该 Bean 名即函数定义名（`sms`）。在配置中 `spring.cloud.function.definition=sms` 声明了该函数是消息处理器，它自动绑定到输入通道 `sms-in-0`（因为函数名 + `-in-0` 是 Spring Cloud Stream 的默认命名规则）。当消息到达 `sms-topic` 时，该 Consumer 会被触发，打印日志。

## 5. 配置细节解读
以 `application-kafka.yml` 为例：
```yaml
spring.cloud.stream:
  default-binder: kafka
  bindings:
    sms-out-0:
      destination: sms-topic
      content-type: application/json
    sms-in-0:
      destination: sms-topic
      group: sms-group
```
- `default-binder` 指定默认使用 Kafka Binder。
- 输出和输入通道都指向同一个 destination，即 Kafka Topic `sms-topic`。
- 输入通道指定 `group`，用于消费者组负载均衡和 offset 管理。
- NATS 和 Rabbit 配置类似，但各自有专属连接参数（`nats.spring.server`、`spring.rabbitmq`）。

## 6. 小结
该示例完美诠释了“一次编写，到处运行”的消息中间件抽象。开发者只需关注业务逻辑（`SmsMessage` 的处理），而将底层基础设施差异交给 Spring Cloud Stream 处理。接下来我们将深入剖析各中间件的配置差异及注意事项。
