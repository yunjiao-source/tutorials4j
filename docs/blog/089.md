## 2. 限流模型：固定窗口计数为什么够用

常见的限流算法有四类：

| 算法 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| 固定窗口计数 | 每个时间窗一个计数器 | 实现最简单、Redis 开销小 | 窗口交界处可瞬时双倍突发 |
| 滑动窗口日志 | 记录每次请求时间戳 | 精确 | 内存/Redis 占用随请求量增长 |
| 滑动窗口计数 | 上一窗口比例 + 当前窗口计数 | 精度与成本折中 | 实现复杂 |
| 令牌桶/漏桶 | 匀速放行 + 桶容量 | 平滑突发流量 | 需要持续的桶状态 |

oauth-core 选择的是 **固定窗口计数**，并且是"分钟 + 天"两个窗口叠加：

- **分钟窗口**负责挡住瞬时突发（如 10 次/分钟），配合 `PEXPIRE 1 分钟` 自动复位；
- **天窗口**负责总量控制（如 10000 次/天），配合 `PEXPIRE 1 天` 自动复位。

对 API Key 配额这类"防滥用 + 计费上限"场景，固定窗口在绝大多数时候足够，且每条计数只占一个 Redis Key、一次 Lua 调用，成本极低。窗口交界处的轻微毛刺（如 59:59 与 00:00 各打满 5 次）在分钟/天的尺度上通常可以接受；如果业务要求严格平滑，第 7 节给出了演进路线。

## 3. ApiKeyRateLimiterService：双窗口计数的实现

`ApiKeyRateLimiterService` 全类不足 50 行，但承载了限流的所有核心决策。先看整体：

```java
@RequiredArgsConstructor
public class ApiKeyRateLimiterService {
  private static final String MINUTE = "minute:";
  private static final String DAILY = "daily:";
  private final RedisScriptExecutor redisScriptExecutor;
  private final ApiKeyOptions apiKeyOptions;

  public boolean allowMinuteRequest(String limiterName, String apiKeyValue) {
    ApiKeyLimiterOptions options = getLimiterOptions(limiterName);
    String key = generateKey(MINUTE, apiKeyValue);

    long count = redisScriptExecutor.incrAndExpire(key, Duration.ofMinutes(1).toMillis());
    return count <= options.getMaxRequestsPerMinute();
  }

  public boolean allowDailyRequest(String limiterName, String apiKeyValue) {
    ApiKeyLimiterOptions options = getLimiterOptions(limiterName);
    String key = generateKey(DAILY, apiKeyValue);

    long count = redisScriptExecutor.incrAndExpire(key, Duration.ofDays(1).toMillis());
    return count <= options.getMaxRequestsPerDay();
  }

  private String generateKey(String type, String apiKeyValue) {
    String keyPrefix = apiKeyOptions.getKeyPrefix();
    return keyPrefix + type + apiKeyValue;
  }

  private ApiKeyLimiterOptions getLimiterOptions(String limiterName) {
    ApiKeyLimiterOptions options = apiKeyOptions.getNamedLimiter().get(limiterName);
    return options == null ? apiKeyOptions.getDefaultLimiter() : options;
  }
}
```

两个 `allowXxxRequest` 方法结构完全对称，可以抽象成同一套四步流水线：

```
1. 取配额    getLimiterOptions(limiterName)      → 命中 namedLimiter，否则 defaultLimiter
2. 拼 Key    keyPrefix + "minute:"/"daily:" + apiKey
3. 原子计数  redisScriptExecutor.incrAndExpire(key, 窗口毫秒数)
4. 阈值比较  count <= maxRequestsPerXxx  → 放行 true / 拒绝 false
```

### 3.1 Key 设计：一个可读、可隔离的命名空间

`generateKey` 产出的 Key 形如：

```
oauth:apikey:minute:sk-123456
oauth:apikey:daily:sk-123456
```

三段式结构各有讲究：

- **`oauth:apikey:`**（`ApiKeyOptions.keyPrefix`，可配置）——业务命名空间。即便与其它模块、其它应用共用 Redis，也不会互相污染；`redis-cli --scan --pattern 'oauth:apikey:*'` 即可盘点全部限流 Key。
- **`minute:` / `daily:`**——窗口维度隔离。同一个 API Key 的分钟计数与天计数互不覆盖，这是"双窗口"能够独立成立的前提。
- **`apiKeyValue`**——调用方维度。**配额按 Key 划分**，同一份 Redis 数据天然支撑成千上万个调用方互不影响。

因为底层走的是 `StringRedisTemplate`（纯字符串序列化），Key 在 Redis 中以明文可读的形式呈现，调试期 `GET` / `TTL` 一目了然，不会出现 JDK 序列化乱码。

### 3.2 配额解析：命名配额表 + 默认兜底

`getLimiterOptions` 是整套"命名限流"的枢纽：

```java
private ApiKeyLimiterOptions getLimiterOptions(String limiterName) {
  ApiKeyLimiterOptions options = apiKeyOptions.getNamedLimiter().get(limiterName);
  return options == null ? apiKeyOptions.getDefaultLimiter() : options;
}
```

`limiterName` 来自 `@ApiKeyRateLimiter(name = "xxx")`。这意味着配额分组的最小单位是"接口/限流组"，而非"调用方"：

- 同一个限流组（name）下的所有调用方共享同一套阈值，但**计数 Key 仍按调用方分开**——例如"普通套餐"组每个 Key 每分钟 10 次，"VIP 套餐"组每个 Key 每分钟 100 次；
- 未在 `namedLimiter` 中声明的 name，自动回退 `defaultLimiter`。**新增接口即使忘记配置，也会被默认配额兜底**，不会出现"忘了配就无限流"的安全漏洞。

## 4. 原子性基石：incrAndExpire 与 Lua 脚本

限流最怕的就是"并发下计数丢失"。经典的错误写法是：

```java
// ❌ 非原子：INCR 与 EXPIRE 之间进程可能崩溃，导致 Key 永不过期
long count = redisTemplate.opsForValue().increment(key);
if (count == 1) redisTemplate.expire(key, Duration.ofMinutes(1));
```

oauth-core 没有重造轮子，而是复用了 `cache-redis` 模块的 `RedisScriptExecutor`，其 `incrAndExpire` 实现如下：

```java
public long incrAndExpire(String key, long expireMills) {
  String newKey = wrapKey(key);
  RedisScript<Long> script =
      scripts.computeIfAbsent(ScriptType.INCR_AND_EXPIRE, ScriptType::getScript);

  Long response =
      redisTemplateDecorator
          .getStringRedisTemplate()
          .execute(script, List.of(newKey), String.valueOf(expireMills));
  return response == null ? 0 : response;
}
```

对应的 Lua 脚本 `incr_and_expire.lua` 只有 7 行：

```lua
-- KEYS[1] : 要操作的 key
-- ARGV[1] : 过期时间（毫秒）
local current = redis.call('INCR', KEYS[1])
if current == 1 then
    redis.call('PEXPIRE', KEYS[1], ARGV[1])
end
return current
```

这段脚本值得逐行解读：

1. `INCR` 原子自增并返回**自增后的新值**——第一个请求拿到 1，第 N 个请求拿到 N；
2. **只有当 `current == 1`（本窗口内首次请求）时才设置 `PEXPIRE`**——窗口锚点取"窗口内第一次请求"而非"整点"，天然避免了时钟对齐问题，也让每次请求都只产生一次 `PEXPIRE` 写操作；
3. 自增与过期设置被放进同一个 Lua 脚本，Redis 单线程执行脚本保证**原子性**——进程崩溃、并发竞争都不会造成"计数了却没设过期"的半成品状态。

`RedisScriptExecutor` 还有一层工程化优化：`ScriptType` 枚举把脚本路径与 `RedisScript<Long>` 实例绑定，执行器用 `ConcurrentHashMap` 按脚本类型缓存实例，避免每次请求都重新解析脚本文本：

```java
public enum ScriptType {
  SET_IF_ABSENT("scripts/set_if_absent.lua"),
  CHECK_AND_SET("scripts/check_and_set.lua"),
  DELETE_IF_SAME("scripts/delete_if_same.lua"),
  INCR_AND_EXPIRE("scripts/incr_and_expire.lua"),
  CHECK_AND_RESET_EXPIRE("scripts/check_and_reset_expire.lua");
  ...
}
```

由于计数和阈值比较发生在**同一个 Java 方法调用内、依赖 Redis 返回的单调递增计数**，即使服务多实例部署（水平扩容、K8s 多副本），只要共享同一个 Redis，限流判定依然全局一致——这是把状态放 Redis、而非 JVM 内存的根本收益。

## 5. 拦截器链路：注解 → 提取 Key → 双窗口校验

`ApiKeyRateLimiterInterceptor` 实现 `HandlerInterceptor`，把上述服务挂进请求生命周期。核心是 `preHandle`，在 Controller 方法执行**之前**完成判定：

```java
@Override
public boolean preHandle(
    HttpServletRequest request, HttpServletResponse response, Object handler) {
  if (log.isDebugEnabled()) {
    log.debug("API KEY 限制处理, method={}, uri={}", request.getMethod(), request.getRequestURI());
  }

  ApiKeyRateLimiter apiKeyRateLimiter =
      WebUtils.getHandlerMethodAnnotation(handler, ApiKeyRateLimiter.class);
  if (ObjectUtils.isNotEmpty(apiKeyRateLimiter)) {
    String apiKeyValue = extractApiKey(request);
    if (StringUtils.isBlank(apiKeyValue)) {
      throw OAuthErrorCode.API_KEY_VALUE_NOT_EXIST.throwed();
    }

    if (!apiKeyRateLimiterService.allowMinuteRequest(apiKeyRateLimiter.name(), apiKeyValue)) {
      throw BaseErrorCode.TOO_MANY_REQUESTS.throwed("API Key 每分钟请求次数超限");
    }

    if (!apiKeyRateLimiterService.allowDailyRequest(apiKeyRateLimiter.name(), apiKeyValue)) {
      throw BaseErrorCode.TOO_MANY_REQUESTS.throwed("API Key 每日请求次数超限");
    }

    response.setHeader(DefaultConsts.HTTP_HEADER_API_KEY_LIMIT, "Pass");
  }

  return true;
}
```

执行流可以拆成五个阶段：

### 阶段 1：注解探测（声明式开关）

```java
ApiKeyRateLimiter apiKeyRateLimiter =
    WebUtils.getHandlerMethodAnnotation(handler, ApiKeyRateLimiter.class);
```

`WebUtils.getHandlerMethodAnnotation` 是 web-core 提供的通用工具：只有 `handler` 是 `HandlerMethod`（即真正命中了某个 Controller 方法）时才反射获取方法上的注解，静态资源等非 HandlerMethod 请求直接返回 `null`：

```java
public static <T extends Annotation> T getHandlerMethodAnnotation(
    Object handler, Class<T> clazz) {
  Method method = null;
  if (handler instanceof HandlerMethod handlerMethod) {
    method = handlerMethod.getMethod();
  }
  if (method == null) {
    return null;
  }
  return method.getAnnotation(clazz);
}
```

没有注解 → 本次请求**直接放行**（`return true`），拦截器退化为透明的观察者。这就是上一篇文章提到的"注册期路径 + 运行期注解"双开关：注解没标对路径，最多是不生效，绝不会误伤其它接口。

### 阶段 2：API Key 提取（三级降级策略）

`extractApiKey` 支持三种携带方式，按优先级依次尝试：

```java
private String extractApiKey(HttpServletRequest request) {
  // 方式1：?apikey=sk-xxx（GET 参数）
  String apiKey = request.getParameter("apikey");
  if (apiKey != null && !apiKey.isEmpty()) return apiKey;

  // 方式2：Authorization: Bearer sk-xxx 或 Authorization: sk-xxx
  String auth = HeaderUtils.getHeader(request, DefaultConsts.HTTP_HEADER_AUTHORIZATION);
  if (auth != null && !auth.isEmpty()) {
    if (auth.startsWith("Bearer ")) {
      return auth.substring(7); // 去掉 "Bearer " 前缀
    }
    return auth;
  }

  // 方式3：apikey: sk-xxx（自定义 Header）
  apiKey = HeaderUtils.getHeader(request, DefaultConsts.HTTP_HEADER_API_KEY);
  if (apiKey != null && !apiKey.isEmpty()) return apiKey;

  return null;
}
```

| 优先级 | 携带方式 | 示例 |
|---|---|---|
| 1 | URL 查询参数 | `GET /api-key?apikey=sk-123` |
| 2 | `Authorization` 头 | `Authorization: Bearer sk-123` 或 `Authorization: sk-123` |
| 3 | 自定义头 | `X-Api-Key: sk-123`（常量 `DefaultConsts.HTTP_HEADER_API_KEY`） |

兼容三种形态，能让同一套限流同时服务"浏览器直接访问（query）""OpenAI 风格客户端（Bearer）"与"网关透传（X-Api-Key）"三类调用方。注意从头里取值用的是公共工具 `HeaderUtils.getHeader`，只取第一个值且不区分大小写语义由 Servlet 容器保证。

### 阶段 3：缺 Key 即拒绝

```java
if (StringUtils.isBlank(apiKeyValue)) {
  throw OAuthErrorCode.API_KEY_VALUE_NOT_EXIST.throwed();
}
```

被限流的接口**必须**携带 API Key——对"没有 Key 的调用方"先做硬性拦截，避免绕过限流直接打到后端（例如把 Key 放在请求体里的调用方，会被此处直接拒绝）。

### 阶段 4：分钟 + 天两次判定

```java
if (!apiKeyRateLimiterService.allowMinuteRequest(apiKeyRateLimiter.name(), apiKeyValue)) {
  throw BaseErrorCode.TOO_MANY_REQUESTS.throwed("API Key 每分钟请求次数超限");
}
if (!apiKeyRateLimiterService.allowDailyRequest(apiKeyRateLimiter.name(), apiKeyValue)) {
  throw BaseErrorCode.TOO_MANY_REQUESTS.throwed("API Key 每日请求次数超限");
}
```

分钟先于天校验：被两个窗口同时拒绝时，优先暴露"分钟超限"这个更紧急、更常见的原因。校验通过与否通过 `throw` 中断表达——**不放行就是抛异常，绝无"半放行"状态**，比返回布尔值再让调用方判断要安全得多。

### 阶段 5：放行标记

```java
response.setHeader(DefaultConsts.HTTP_HEADER_API_KEY_LIMIT, "Pass");
```

限流通过后写入响应头 `X-Api-Key-Limit: Pass`。这个头的意义在于**让网关/客户端无需解析响应体**就能感知"本次请求经过了限流检查"，例如反向代理可以据此统计真实放行量，客户端可以据此判断是"限流放行"还是"业务成功"。

## 6. 计数语义与边界行为

固定窗口计数的一个微妙点是**先计数、后比较**。以 `maxRequestsPerMinute = 5` 为例，逐请求推演：

| 请求序号 | Redis 计数（INCR 后） | 判定 | 结果 |
|---|---|---|---|
| 1 | 1 | 1 ≤ 5 | ✅ 放行 |
| 2 | 2 | 2 ≤ 5 | ✅ 放行 |
| … | … | … | ✅ 放行 |
| 5 | 5 | 5 ≤ 5 | ✅ 放行（窗口内最后一个名额） |
| 6 | 6 | 6 > 5 | ❌ 429 拒绝 |

行为特征：

- **第 1 次请求触发建 Key + PEXPIRE**，窗口锚点即"首次请求时刻"，之后 `PEXPIRE` 不再执行，直到 Key 自然过期被 Redis 回收；
- **窗口过期后第一个请求**重新从 1 计数，配额自动满血复活，无需任何"清零"定时任务；
- **超限请求也执行了 INCR**，所以计数会继续增长（6、7、8…），但对判定无副作用——这保证窗口内无论如何都不会"多放行"；
- 拦截器在窗口内对超限请求**立即 429**，不会穿透到 Controller，因此超限流量几乎不消耗后端线程与数据库连接。

异常映射回顾（细节见 088 第 5 节）：分钟/天超限抛 `BaseErrorCode.TOO_MANY_REQUESTS` → 全局异常处理器映射为 **HTTP 429**；缺 Key 抛 `OAuthErrorCode.API_KEY_VALUE_NOT_EXIST` → 未注册映射时兜底 **HTTP 422**，响应体为统一 `Result` 结构。

## 7. 局限性与生产化改进方向

固定窗口并非银弹，基于源码可以指出几个已知边界与演进路径：

1. **窗口交界突发**：同一 Key 可在窗口 A 末打满、窗口 B 初立刻再打满。若业务敏感，可把分钟窗口升级为**滑动窗口计数**（记录上一窗口计数 + 当前窗口计数按时间比例加权），Lua 脚本同样能原子完成。
2. **配额粒度单一**：目前 Key 只含"调用方"，不含租户、地域等维度。扩展方式是在 `generateKey` 中追加维度段，例如 `oauth:apikey:minute:tenant-1:sk-123`，服务签名不变、Key 语义更丰富。
3. **超限反馈信息有限**：429 只带文案，客户端无法得知"何时能重试"。可仿照 `Retry-After` 语义，在响应头中输出窗口剩余秒数；或为 `Result` 增加 `retryAfterMillis` 字段。
4. **可观测性**：目前没有限流命中计数。可在拦截器拒绝分支埋点（Micrometer Counter + Tag 区分"缺 Key/分钟超限/天超限"），与 Prometheus 打通（examples-oauth 已引入 actuator + prometheus 依赖，可直接扩展）。
5. **配额热更新**：`namedLimiter` 是启动时绑定的静态配置，运行时改 YAML 需重启。生产环境可引入配置中心（Nacos/Apollo）驱动刷新，或把配额表下沉到 Redis Hash 由控制台维护。

## 8. 总结

从本文的源码走读可以看到，oauth-core 的限流实现遵循三条朴素原则：

- **状态放 Redis、逻辑放 Lua**：计数、过期、比较全部围绕原子脚本展开，多实例部署天然一致；
- **声明式接入、命令式兜底**：注解声明"限不限"，拦截器负责"必须执行"，缺 Key 与超限都是硬失败；
- **错误即异常**：不放行就用错误码中断，交给统一异常体系翻译成标准 `Result` 与 HTTP 状态码。
