# 092-功能模块-API Key 生命周期管理实战：创建、更新、查询与删除的完整实现

## 1. 引言

上一篇（091）梳理了 `feature-sa-token` 的整体架构：注解启用、JPA 实体、Specification 动态查询、命名空间模板工厂与"数据库 + Sa-Token 插件"的分工。本文进入源码级拆解，看 API Key 从"出生"到"回收"的完整生命周期是如何实现的：

```
创建(create) → 查询(list/page) → 更新(update) → 删除(delete/deleteAll)
     │              │                  │               │
     └── ApiKeyComponent（事务边界 + 归属校验）
            │
            ├── SaApiKeyTemplateFactory → 按命名空间取模板
            │
            ├── SaApiKeyTemplateDatabase → DB 持久化 + 缓存同步

```

我们将依次剖析：**模型转换器 → 数据库模板与加载器 → 业务编排组件 → REST 接口 → 双写一致性**，最后给出可运行的端到端演示。

## 2. 模型转换器：ApiKeyModel ↔ ApiKeyEntity

插件的运行时模型 `ApiKeyModel`（标题/介绍/Key/归属/时间/有效位/Scopes/扩展数据）与 JPA 实体 `ApiKeyEntity` 字段并不完全同构，差异集中在三处：

| 差异 | ApiKeyModel | ApiKeyEntity |
|---|---|---|
| 归属字段类型 | `Object loginId` | `String loginId` |
| 创建时间 | `long createTime`（13 位毫秒） | `Instant createDate`（审计字段） |
| 扩展数据值类型 | `Map<String, Object>` | `Map<String, String>`（JSON 列） |

`ApiKeyModelConverter` 用两个静态方法完成双向转换：

```java
public interface ApiKeyModelConverter {
  // 实体 → 插件模型
  static ApiKeyModel convert(ApiKeyModel model, ApiKeyEntity entity) {
    BeanUtils.copyProperties(entity, model);          // 拷贝同名属性
    if (!CollectionUtils.sizeIsEmpty(entity.getExtraData())) {
      entity.getExtraData().forEach(model::addExtra);  // 逐条并入扩展数据
    }
    if (entity.getCreatedDate() != null) {
      model.setCreateTime(entity.getCreatedDate().toEpochMilli()); // 审计时间 → 13位时间戳
    }
    model.setLoginId(entity.getLoginId());
    return model;
  }

  // 插件模型 → 实体
  static ApiKeyEntity convert(ApiKeyEntity entity, ApiKeyModel model) {
    BeanUtils.copyProperties(model, entity);
    if (!CollectionUtils.sizeIsEmpty(model.getExtraData())) {
      model.getExtraData().forEach(
          (k, v) -> entity.getExtraData().put(k, v == null ? null : v.toString())); // 值统一转字符串
    }
    if (model.getCreateTime() > 0) {
      entity.setCreatedDate(TimeUtil.toInstant(model.getCreateTime())); // 毫秒 → Instant（Asia/Shanghai）
    }
    if (model.getLoginId() != null) {
      entity.setLoginId(model.getLoginId().toString()); // 任意类型登录号统一字符串化
    }
    return entity;
  }
}
```

值得注意的细节：

- `loginId` 统一做 `toString()`：Sa-Token 允许任意类型登录号（常用 Long），入库与比对都以字符串为规范，避免 `10001`（数字）与 `"10001"` 因类型不同而误判为不同用户；
- `extraData` 值统一转 `String` 落库（数据库列是 JSON 字符串），读回时经 `HashMapConverter` 反序列化还原；
- 时间只保留一个事实源：**实体审计字段 `createDate` ↔ 模型 13 位毫秒 `createTime`**，转换使用框架 `TimeUtil` 统一 Asia/Shanghai 时区。

## 3. 数据库模板：SaApiKeyTemplateDatabase 覆写四件套

`SaApiKeyTemplateDatabase` 继承插件的 `SaApiKeyTemplate`，把"内存/缓存操作"扩展为"数据库操作 + 缓存同步"，共覆写四个方法。

### 3.1 getApiKeyList：列表以数据库为准

插件默认的 `getApiKeyList` 依赖"按用户索引"（`getIsRecordIndex=true` 时才可用），而我们关闭了索引（见第 4 节），因此改为直查数据库：

```java
@Override
public List<ApiKeyModel> getApiKeyList(Object loginId) {
  Assert.notNull(loginId, "loginId must not be null");
  return apiKeyRepository.findByNamespaceAndLoginId(namespace, loginId.toString()).stream()
      .map(e -> ApiKeyModelConverter.convert(new ApiKeyModel(), e))
      .toList();
}
```

### 3.2 saveApiKey：写库 + 回写缓存（幂等 upsert）

```java
@Override
@Transactional(rollbackFor = Exception.class)
public void saveApiKey(ApiKeyModel apiKeyModel) {
  if (apiKeyModel == null) {
    return;
  }
  ApiKeyEntity entity =
      apiKeyRepository
          .findByNamespaceAndApiKeyAndLoginId(
              namespace, apiKeyModel.getApiKey(), apiKeyModel.getLoginId().toString())
          .orElse(new ApiKeyEntity());
  ApiKeyModelConverter.convert(entity, apiKeyModel);
  entity.setNamespace(namespace);
  apiKeyRepository.save(entity);
  super.saveApiKey(apiKeyModel);   // ← 关键：同步插件缓存
}
```

- **幂等 upsert**：按 `(namespace, apiKey, loginId)` 查找，存在则更新、不存在则新建——创建与更新走同一条路径；
- `namespace` 由模板实例注入（`new ApiKeyEntity()` 时 entity 的 namespace 为空，这里统一补上），保证数据归属正确；
- **调用 `super.saveApiKey`** 把模型写回 Sa-Token 缓存（`${tokenName}:${namespace}:${apiKey}`，TTL = 剩余有效期；已过期的模型在父类中会执行删除而非写入）。这样运行时校验（`getApiKey`）不需要每次都穿透数据库；
- 方法标注 `@Transactional(rollbackFor = Exception.class)`，保证**先落库、后缓存**，DB 是事实来源。

### 3.3 deleteApiKey：删库 + 清缓存

```java
@Override
@Transactional(rollbackFor = Exception.class)
public void deleteApiKey(String apiKey) {
  apiKeyRepository.findByApiKey(apiKey).ifPresent(e -> apiKeyRepository.deleteById(e.getId()));
  super.deleteApiKey(apiKey);  // 同步移除缓存中的模型
}
```

按 `apiKey` 直接定位记录删除（`api_key` 列有唯一约束），随后 `super.deleteApiKey` 把缓存中的模型一并清除，避免"数据库已删、缓存仍可校验通过"的窗口。

### 3.4 deleteApiKeyByLoginId：按用户批量回收

```java
@Override
@Transactional(rollbackFor = Exception.class)
public void deleteApiKeyByLoginId(Object loginId) {
  Assert.notNull(loginId, "loginId must not be null");
  List<ApiKeyEntity> entities = apiKeyRepository.findByNamespaceAndLoginId(namespace, loginId.toString());
  apiKeyRepository.deleteByNamespaceAndLoginId(namespace, loginId.toString()); // 批量删库

  for (ApiKeyEntity entity : entities) {
    super.deleteApiKey(entity.getApiKey());  // 逐个清缓存
  }
}
```

先查出该命名空间下该用户的所有 Key 实体，批量删库，再**逐个**清除缓存（父类不支持"按用户批量删缓存"，因为索引已关闭），保证双端一致。

## 4. 数据加载器：SaApiKeyDataLoaderDatabase

模板的 `getApiKey` 走"先缓存、未命中回源"路径时，会调用全局 `SaApiKeyManager.getSaApiKeyDataLoader()`，本模块用数据库加载器替换了默认实现：

```java
public class SaApiKeyDataLoaderDatabase implements SaApiKeyDataLoader {
  private final ApiKeyRepository apiKeyRepository;

  @Override
  public Boolean getIsRecordIndex() {
    return false;   // 关闭"按用户索引"，索引职责交给数据库
  }

  @Override
  public ApiKeyModel getApiKeyModelFromDatabase(String namespace, String apiKey) {
    Assert.hasText(namespace, "namespace must not be null or empty");
    Assert.hasText(apiKey, "apiKey must not be null or empty");
    return apiKeyRepository
        .findByNamespaceAndApiKey(namespace, apiKey)
        .map(e -> ApiKeyModelConverter.convert(new ApiKeyModel(), e))
        .orElse(null);
  }
}
```

两个方法分别对应插件数据加载器接口的两个语义：

1. **`getIsRecordIndex() = false`**：告诉插件"不要维护用户 → Key 列表的内存索引"。这直接改变了父类若干方法的行为——例如父类 `getApiKeyList` 未开启索引时会告警并返回空列表（所以模块自己覆写了它），`deleteApiKeyByLoginId` 也必须由子类自己实现（正是第 3.4 节的内容）；
2. **`getApiKeyModelFromDatabase(namespace, apiKey)`**：按命名空间 + Key 精确回源，命中后由父类 `getApiKey` 自动回填缓存。

由此形成完整的读取链：

```
业务校验 getApiKey(apiKey)
   ├─ ① 查缓存 getApiKeyModelFromCache  → 命中直接返回
   ├─ ② 未命中 → SaApiKeyDataLoaderDatabase.getApiKeyModelFromDatabase(namespace, apiKey)
   └─ ③ 数据库命中 → saveApiKey 回填缓存（带 TTL），再返回
```

## 5. 业务编排：ApiKeyComponent

`ApiKeyComponent` 是管理接口背后的"门面"，所有方法都以 `@Transactional` 包裹，并内置**归属校验**：

```java
@Component
@RequiredArgsConstructor
public class ApiKeyComponent {
  private final SaApiKeyTemplateFactory saApiKeyTemplateFactory;

  @Transactional(rollbackFor = Exception.class)
  public ApiKeyModel create(ApiKeyCreateModel model) {
    SaApiKeyTemplate saApiKeyTemplate = saApiKeyTemplateFactory.getTemplate(model.getNamespace());
    ApiKeyModel apiKeyModel = saApiKeyTemplate.createApiKeyModel(model.getLoginId());
    model.fillTo(apiKeyModel);
    saApiKeyTemplate.saveApiKey(apiKeyModel);   // 落库 + 回写缓存
    return apiKeyModel;
  }

  @Transactional(rollbackFor = Exception.class)
  public ApiKeyModel update(ApiKeyUpdateModel model) {
    SaApiKeyTemplate saApiKeyTemplate = saApiKeyTemplateFactory.getTemplate(model.getNamespace());
    saApiKeyTemplate.checkApiKeyLoginId(model.getApiKey(), model.getLoginId()); // 归属校验
    ApiKeyModel apiKeyModel = saApiKeyTemplate.getApiKey(model.getApiKey());
    model.fillTo(apiKeyModel);
    saApiKeyTemplate.saveApiKey(apiKeyModel);
    return apiKeyModel;
  }

  public List<ApiKeyModel> list(String namespace, Object loginId) { ... }

  @Transactional(rollbackFor = Exception.class)
  public void delete(String namespace, Object loginId, String apiKey) {
    saApiKeyTemplate.checkApiKeyLoginId(apiKey, loginId);
    saApiKeyTemplate.deleteApiKey(apiKey);
  }

  @Transactional(rollbackFor = Exception.class)
  public void deleteAll(String namespace, Object loginId) {
    saApiKeyTemplate.deleteApiKeyByLoginId(loginId);
  }
}
```

几个实现语义：

- **创建**：`createApiKeyModel(loginId)` 由插件生成随机密钥——默认前缀 `AK-` + 36 位随机串，`isValid=true`，`expiresTime = 当前时间 + 默认有效期`（Sa-Token 默认 30 天，可配置），随后 `fillTo` 只覆盖标题/简介/Scopes/扩展数据（**创建时不允许调用方指定过期时间与有效位**，过期策略由全局配置兜底，防止"永不过期"密钥被随意创建）；
- **更新与删除都先做 `checkApiKeyLoginId`**：插件方法会先校验该 Key 是否存在（无效返回 12301），再校验是否属于指定 `loginId`（不属于返回 12312）——这是"防越权"的第一道闸：**普通用户只能操作自己的 Key**；
- 模板实例按 `namespace` 从工厂取，因此**同一个 ApiKeyComponent 服务多套命名空间的 Key 池**，彼此互不可见。

## 6. REST 接口：三种视角的管理端点

模块把管理能力拆成三组 Controller，覆盖"管理员 / 当前用户 / 查询者"三种视角：

| 分组 | 路径前缀 | 语义 |
|---|---|---|
| `ApiKeyController`（管理端） | `/api/sa-token/api-key` | 创建/更新/删除可指定任意 `loginId`（供管理员） |
| `CurrentApiKeyController`（我的） | `/api/sa-token/api-key-current` | 面向当前登录用户，`loginId` 一律取自会话 |
| `QueryApiKeyController`（查询端） | `/api/sa-token/api-key-query` | 分页/按 ID 只读查询（含管理后台列表） |

### 6.1 校验分组：AdminGroup vs UserGroup

DTO 上 `loginId` 的必填约束按分组声明（`ApiKeyCreateModel` 片段）：

```java
@NotNull(message = "loginId是必须的", groups = ValidGroup.AdminGroup.class)
private Object loginId;
```

- 管理端接口用 `@Validated(ValidGroup.AdminGroup.class)` 校验——**必须显式提供 loginId**；
- 当前用户接口用 `@Validated(ValidGroup.UserGroup.class)` 校验——loginId 可以省略，Controller 统一从会话注入：

```java
@PostMapping("create")
public Result<ApiKeyModel> create(
    @Validated(ValidGroup.UserGroup.class) @RequestBody ApiKeyCreateModel model) {
  model.setLoginId(StpUtil.getLoginId());   // 从当前会话取，调用方无法伪造
  ...
}
```

这一设计的价值在于：**"操作谁的数据"由会话决定，而不是由请求体决定**，从源头堵住越权。

### 6.2 典型请求示例（管理端）

```bash
# 创建（管理员为 10001 用户签发一个 Key）
curl -X POST http://localhost:8080/api/sa-token/api-key/create \
  -H 'Content-Type: application/json' \
  -d '{
    "namespace": "default",
    "loginId": 10001,
    "title": "开放平台-订单服务",
    "intro": "生产环境密钥",
    "scopes": ["order:read", "order:write"],
    "extraData": {"env": "prod"}
  }'
```

响应由框架统一 `Result` 包装并携带完整模型，其中 `apiKey` 即签发的密钥（仅此一次明文返回，请提示调用方妥善保存；成功响应的 code/message 填充约定与 088 篇第 5 节的统一响应体系一致）：

```json
{
  "timestamp": "...",
  "data": {
    "title": "开放平台-订单服务",
    "intro": "生产环境密钥",
    "apiKey": "AK-U9x3kL...36位随机串...",
    "loginId": "10001",
    "createTime": 1752...,
    "expiresTime": 1752...,
    "isValid": true,
    "scopes": ["order:read", "order:write"],
    "extraData": {"env": "prod"}
  }
}
```

更新要求全量提交（`isValid`、`expiresTime`、`title` 必填，`expiresTime` 为毫秒时间戳）：

```bash
curl -X PUT http://localhost:8080/api/sa-token/api-key/update \
  -H 'Content-Type: application/json' \
  -d '{
    "namespace": "default",
    "loginId": 10001,
    "apiKey": "AK-...",
    "isValid": false,
    "expiresTime": 1755...,
    "title": "开放平台-订单服务（已停用）",
    "scopes": ["order:read"]
  }'
```

删除与查询：

```bash
# 删除单个（校验归属）
curl -X DELETE "http://localhost:8080/api/sa-token/api-key?namespace=default&loginId=10001&apiKey=AK-..."

# 删除某用户全部
curl -X DELETE "http://localhost:8080/api/sa-token/api-key/all?namespace=default&loginId=10001"

# 分页查询（条件：namespace/title/loginId/isValid/createTimeBegin/createTimeEnd + page/size）
curl "http://localhost:8080/api/sa-token/api-key-query/page?namespace=default&title=订单&page=0&size=10"

# 按 ID 查询
curl "http://localhost:8080/api/sa-token/api-key-query/{id}"
```

### 6.3 会话保护与异常语义

- "我的"端点依赖 `StpUtil.getLoginId()`：未登录访问会抛 `NotLoginException`，由 `oauth-sa-token` 的 `SaTokenExceptionHandler` 统一转成 **HTTP 401 + Result** 响应；
- 管理端与查询端是否需要登录/权限，由接入方通过 Sa-Token 的 `SaInterceptor`、`@SaCheckLogin` / `@SaCheckPermission` 注解或路由过滤器自行声明（Sa-Token 的能力在 oauth-sa-token 中已桥接好）——**feature-sa-token 专注 Key 本身的管理语义，不越权决定接口的开放策略**。

## 7. 一致性分析：数据库与缓存的双写边界

回看全部写路径，模块的一致性策略是"**数据库先行、缓存跟随**"：

| 操作 | 数据库 | 缓存（super 调用） |
|---|---|---|
| create / update | upsert 后提交事务 | 写入模型并带 TTL；已过期则删除 |
| delete 单个 | 删除记录 | 立即清除对应模型 |
| delete 全部 | 批量删除 | 逐个清除 |

风险与对策：

1. **缓存写失败**：DB 提交成功、缓存写入失败（Redis 抖动）时，读侧有兜底——`getApiKey` 缓存未命中会自动回源数据库并回填，因此**最多损失一次性能，不会读到脏数据**；
2. **删除后的短暂缓存残留**：`deleteApiKey` 已通过 `super` 即时清缓存，理论上无残留窗口；若极端情况下清理失败，缓存模型也会因 TTL 到期自然消失；
3. **事务边界提醒**：`@Transactional` 只覆盖数据库操作，`super.saveApiKey`（写 Sa-Token 缓存/Redis）不在同一事务内。对一致性要求更高的场景，可演进为"先失效缓存、再写库"或引入事件总线补偿，但当前取舍（DB 为准 + 读穿回源）在绝大多数业务下已足够；
4. **明文存储**：`feat_api_key` 表存的是 API Key 明文（插件校验需要原文比对/哈希查库）。生产环境建议对 `api_key` 列加密存储或改存哈希并配合插件扩展，属于模块之外的安全加固点。

```bash
./mvnw -pl framework/framework-examples/examples-feature -am spring-boot:run \
  -Dspring-boot.run.profiles=sa-token
```

访问 `http://localhost:8080/api-key` 即进入 **🔑 API Key 管理系统**页面：

1. 用 `zhang / 123456` 登录（会话 loginId = 10001）；
2. **我的 API Keys** 页签：创建 Key（命名空间/标题/简介/Scopes/扩展数据）→ 刷新列表 → 可修改有效位、过期天数（页面按天换算成毫秒）或删除；
3. **管理所有** 页签：以管理员视角为任意 `loginId` 创建/更新/删除 Key（演示前台接口，生产请加权限控制）；

5. **Token 信息** 页签：查看当前 Sa-Token 会话信息，直观理解"登录态"与"API Key"的关系。

数据库侧可通过 `feat_api_key` 表直接观察每次操作的结果（`namespace + loginId` 有复合索引、`api_key` 唯一），也便于演示第 7 节提到的"数据库是唯一事实来源"。

## 9. 与其它模块的协同：从"签发"到"限流"的完整闭环

至此，把 feature-sa-token 与认证授权域的其它能力串起来，就得到一套完整的开放 API 治理链路：

| 环节 | 承担者 | 说明 |
|---|---|---|
| 账号登录 | Sa-Token（oauth-sa-token 桥接） | 会话/权限/踢人下线等 |
| API Key 签发与校验 | feature-sa-token（本模块） | 数据库持久化 + 创建/更新/查询/回收 + `@SaCheckApiKey` 校验 |
| 按 Key 配额限流 | oauth-core（见 088/089/090） | 对携带 API Key 的请求做"分钟 + 天"双窗口 Redis 限流 |

业务接口上既可二选一，也可组合使用：feature-sa-token 回答"**这个 Key 是谁的、有没有效、有没有权限**"，oauth-core 回答"**这个 Key 今天还能不能用、用几次**"。

## 10. 总结

下篇的源码走读可以沉淀出五条可复用的实现经验：

1. **给"第三方插件"做持久化，优先走官方扩展点**：覆写模板生命周期方法 + 实现数据加载器 + 替换全局单例，而不是复制一份实现；
2. **数据库是事实来源，缓存只是加速**：所有写路径 DB 先行、缓存跟随，读路径"缓存 → 数据库 → 回填"闭环，天然抗缓存抖动；
3. **归属校验前置**：更新/删除前用 `checkApiKeyLoginId` 做所有权断言，"我的"端点 loginId 一律取自会话，杜绝越权；
4. **命名空间驱动模板选择**：一套服务代码，任意 Key 池彼此隔离；
5. **把"开放策略"留给接入方**：模块提供密钥治理能力，接口是否需要登录/角色/权限由 Sa-Token 注解与过滤器在业务层声明，保持模块职责单一。

从 088 到 092，认证授权与功能模块两条线的 API Key 能力已经全景呈现：`oauth-core` 管"额度"、`feature-sa-token` 管"密钥"，二者结合即可支撑一个生产级的开放 API 治理后台。
