# 090-OAuth模块-API Key 限流开箱即用：examples-oauth 接入实战与效果演示

本文章代码: [gitee](https://gitee.com/yunjiao-source/tutorials4j) , [gitcode](https://gitcode.com/yun-jiao/tutorials4j) , [github](https://github.com/yunjiao-source/tutorials4j)

## 1. 目标与准备

前两篇文章分别剖析了 `oauth-core` 的架构（088）与限流内部实现（089）。本文换一个视角：**作为使用者，如何在 10 分钟内把"按 API Key 的分钟 + 天双窗口限流"跑起来**，并看懂每个现象背后的机制。

我们使用仓库自带的示例工程 `framework/framework-examples/examples-oauth`，它通过 `profile:apikey` 演示 API Key 限流。动手前请确认：

- JDK 17+ 与 Maven 环境正常（仓库根目录含 `mvnw` 包装器）；
- 本地有可用的 Redis，地址 `localhost:6379`，示例默认使用 **database 2**（`application.yml` 中 `spring.data.redis.database: 2`），避免与本地其它数据冲突；
- 示例需要访问外网 CDN 加载 Bootstrap/jQuery（页面演示部分），仅用 curl 验证则不受影响。

## 2. 示例工程速览

examples-oauth 只引用了两个框架依赖——`oauth-spring-boot-starter`（限流能力）与 `spring-boot-starter-web`（Web 容器），外加 Thymeleaf、actuator 与 Prometheus 注册器用于页面与监控：

```xml
<dependency>
  <groupId>yunjiao-source.tutorials4j.framework</groupId>
  <artifactId>oauth-spring-boot-starter</artifactId>
  <version>${revision}</version>
</dependency>
```

四个源码文件各司其职：

| 文件 | 角色 |
|---|---|
| `ExampleOAuthApplication` | 启动类，`@SpringBootApplication`，无任何额外注解——限流完全由 Starter 自动装配 |
| `ApiKeyConfig` | `@Profile("apikey")` 配置类，仅负责把 `apikey` 包的 Controller 扫进容器 |
| `ApiKeyController` | 被测接口：`GET /api-key`，方法上标注 `@ApiKeyRateLimiter(name = "method1")` |
| `PageController` | `GET /demo` 渲染演示页面 `apikey/demo.html` |

关键接口代码只有 8 行：

```java
@RestController
public class ApiKeyController {

  @GetMapping("api-key")
  @ApiKeyRateLimiter(name = "method1")
  public String method1() {
    return "ok";
  }
}
```

**声明式限流就此完成**——不需要注入任何服务，不需要手写判断逻辑，接口方法本身零侵入。`name = "method1"` 即 089 节中 `getLimiterOptions` 查找 `namedLimiter` 的键。

## 3. 配置解读：配额组与拦截范围

`src/main/resources/application-apikey.yml` 是本次演示的全部配置：

```yaml
tutorials4j:
  oauth:
    api-key:
      default-limiter:
        max-requests-per-day: 20
        max-requests-per-minute: 10
      named-limiter:
        method1:
          max-requests-per-minute: 5
          max-requests-per-day: 10
      interceptor:
        include-path-patterns: /api-key
```

三层配置分别对应三类决策：

1. **`default-limiter`**（10 次/分钟、20 次/天）：全局兜底配额，任何未被 `named-limiter` 覆盖的 name 都走这里；
2. **`named-limiter.method1`**（5 次/分钟、10 次/天）：`name = "method1"` 的接口专属配额，**覆盖默认值**。所以下面的演示都以"每分钟 5 次、每天 10 次"为准；
3. **`interceptor.include-path-patterns: /api-key`**：拦截器只对 `/api-key` 路径生效。注意它覆盖了框架默认值 `{"/demo/**"}`，因此演示页面 `/demo` 本身不会被限流，只有被测接口受保护。

`application.yml` 中 `spring.profiles.active: apikey` 默认激活该 profile；若想手工切换，也可在启动参数中覆盖，例如：

```
java -jar examples-oauth.jar --spring.profiles.active=apikey
```

## 4. 启动与页面演示

### 4.1 启动

先确保 Redis 已启动，然后在 `examples-oauth` 目录执行：

```bash
# Linux/macOS（仓库根目录执行）
./mvnw -pl framework/framework-examples/examples-oauth -am spring-boot:run

# Windows
.\mvnw.cmd -pl framework/framework-examples/examples-oauth -am spring-boot:run
```

启动成功后访问：

- 示例首页：`http://localhost:8080/`
- 限流演示页：`http://localhost:8080/demo`

由于 `application.yml` 将 `tutorials4j` 包日志级别设为 `TRACE`，启动日志中可以看到 oauth 自动装配的痕迹：

```
[OAUTH] OAuth Auto Configuration
[OAUTH-CORE] OAuth Configuration
[OAUTH-CORE] Api Key Rate Limiter Service
[OAUTH-CORE] OAuth MVC Configuration
[OAUTH-CORE] 'ApiKeyRateLimiterInterceptor' configuration parameters are HandlerInterceptorOptions(includePathPatterns=[/api-key], excludePathPatterns=[])
```

### 4.2 页面操作

演示页（`apikey/demo.html`）标题直接写明"每分钟最多 5 次，每天最多 10 次"，输入框默认携带 API Key `my-secret-key`，点击 **🚀 调用 /api-key** 即可发请求：

- 前 5 次：返回 `ok`，绿色提示；
- 第 6 次起：返回 **429**，红色提示"请求次数超限 (最大 5 次)"。

页面里的"🔄 重置计数"按钮调用的是 `/reset` 接口，而示例工程并未实现该端点，重置请使用第 6 节的 Redis 命令（`DEL` 计数 Key）——这也提醒我们：**示例演示了限流，但没有暴露配额管理端点，真实系统需要自行实现或接入控制台**。

## 5. curl 验证：协议层观察

页面演示之外，用 curl 可以把三种 API Key 携带方式、三种失败形态全部验证一遍。

### 5.1 正常放行（三种携带方式等价）

```bash
# 方式1：查询参数
curl -i "http://localhost:8080/api-key?apikey=my-secret-key"

# 方式2：Authorization 头（Bearer / 裸值均可）
curl -i -H "Authorization: Bearer my-secret-key" http://localhost:8080/api-key

# 方式3：X-Api-Key 自定义头
curl -i -H "X-Api-Key: my-secret-key" http://localhost:8080/api-key
```

响应要点：

```
HTTP/1.1 200
X-Api-Key-Limit: Pass          ← 限流放行标记头
```

> 提示：`?apikey=` 的 query 名、`X-Api-Key` 头名均定义在 `DefaultConsts`，属框架约定；若与贵司网关规范冲突，可在拦截器扩展中调整提取逻辑。

### 5.2 缺少 API Key → 422

```bash
curl -i http://localhost:8080/api-key
```

由于 `API_KEY_VALUE_NOT_EXIST` 未在错误码映射表中注册，框架兜底为 422：

```json
{
  "code": "API_KEY_VALUE_NOT_EXIST",
  "message": "缺少 API Key",
  "path": "/api-key",
  "traceId": "...",
  "error": { "detail": null }
}
```

### 5.3 连续调用第 6 次 → 429

```bash
for i in $(seq 1 6); do
  curl -s -o /dev/null -w "第${i}次: HTTP %{http_code}\n" \
    -H "X-Api-Key: my-secret-key" http://localhost:8080/api-key
done
```

输出：

```
第1次: HTTP 200
第2次: HTTP 200
第3次: HTTP 200
第4次: HTTP 200
第5次: HTTP 200
第6次: HTTP 429
```

第 6 次响应体（`BaseErrorCode.TOO_MANY_REQUESTS` 已映射为 429）：

```json
{
  "code": "TOO_MANY_REQUESTS",
  "message": "太多请求",
  "path": "/api-key",
  "error": { "detail": "API Key 每分钟请求次数超限" }
}
```

若把 `method1` 的每天上限改成很小值（或直接调 Redis 把 daily 计数顶到阈值），第 7 次起会看到 `"API Key 每日请求次数超限"` 的 429——两个窗口的判定顺序是分钟优先（详见 089 第 5 节）。

## 6. Redis 侧检视：计数与窗口

打开另一个终端直查 Redis（示例连的是 database 2）：

```bash
redis-cli -n 2 --scan --pattern 'oauth:apikey:*'
```

能看到两个 Key：

```
oauth:apikey:daily:my-secret-key
oauth:apikey:minute:my-secret-key
```

查看计数与剩余存活时间：

```bash
redis-cli -n 2 GET oauth:apikey:minute:my-secret-key   # 例如 5
redis-cli -n 2 TTL  oauth:apikey:minute:my-secret-key  # 例如 42（秒），随窗口自然复位
redis-cli -n 2 GET oauth:apikey:daily:my-secret-key    # 例如 6
redis-cli -n 2 TTL  oauth:apikey:daily:my-secret-key   # 接近 86400（秒）
```

手工"重置配额"（相当于演示页期待的重置动作）：

```bash
redis-cli -n 2 DEL oauth:apikey:minute:my-secret-key oauth:apikey:daily:my-secret-key
```

删除后下一次请求会从 1 重新计数——这正是 Lua 脚本中 `current == 1` 才设置 `PEXPIRE` 的语义：**窗口过期或 Key 被删，配额自动满血，无需任何定时清理任务**。等 60 秒不删 Key，也能观察到分钟 Key 因 TTL 到期被 Redis 自动回收。

## 7. 进阶验证：默认配额与"换个 Key"

如果新增一个 Controller 方法：

```java
@GetMapping("another")
@ApiKeyRateLimiter(name = "free-tier")   // namedLimiter 中没有 free-tier
public String another() {
  return "ok";
}
```

并把拦截范围扩展到它：

```yaml
tutorials4j:
  oauth:
    api-key:
      interceptor:
        include-path-patterns:
          - /api-key
          - /another
```

那么 `free-tier` 组会回退到 `default-limiter`，即 **10 次/分钟、20 次/天**——即使开发者忘了给新接口配置配额，默认值也在兜底。

再做一个实验：把请求头的 Key 换成 `other-key`，会观察到配额独立计算（`oauth:apikey:minute:other-key` 从 1 开始），印证 **"配额按 name 分组、计数按 Key 隔离"** 的双维度设计。

## 8. 常见问题排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 注解加了但完全不限流 | 请求路径不在 `include-path-patterns` 内（双开关之一未闭合） | 检查 `tutorials4j.oauth.api-key.interceptor.include-path-patterns` |
| 返回 422"缺少 API Key" | 请求没带 Key，或带了但三种提取方式都不识别 | 用 `?apikey=`、`Authorization: Bearer xxx` 或 `X-Api-Key` 之一携带 |
| 刚重启计数还在 | Key 有 TTL，窗口未过期 | `redis-cli -n 2 DEL` 对应 Key，或等窗口自然结束 |
| 连不上 Redis 启动报错 | 示例默认连 `localhost:6379` 的 database 2 | 启动本地 Redis，或改 `application.yml` 连接参数 |
| 想改响应头/报错文案 | 拦截器与错误码硬编码于 oauth-core | 参照 088 第 5 节注册自定义错误码映射，或自定义 `ApiKeyRateLimiterService` Bean 覆盖 |

## 9. 总结

通过 examples-oauth 的完整演示，可以看到这套 API Key 限流能力的接入成本几乎为"零"：

- **三步接入**：引入 `oauth-spring-boot-starter` → 方法上加 `@ApiKeyRateLimiter(name = "...")` → YAML 里配配额与拦截路径；
- **开箱即用的默认值**：未配置 name 也有 `default-limiter` 兜底；
- **可观测、可调试**：Key 明文可查、TTL 清晰、`X-Api-Key-Limit: Pass` 头可被网关消费；
- **可扩展**：配额组、携带方式、错误映射都留有清晰的扩展点。

至此，088/089/090 三篇分别从"架构骨架 → 实现细节 → 落地演示"完整覆盖了 `oauth-core` 的 API Key 限流能力。如果要把这套能力接到 Sa-Token 生态（签发/校验 Key），下一步可以研究 `oauth-so-token` 模块的 `SaApiKeyTemplateFactory`，认证与限流即可组成完整闭环。
